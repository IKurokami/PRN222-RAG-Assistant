====================================================================================================
1. TỔNG QUAN HỆ THỐNG
====================================================================================================

PRN222 RAG Assistant là ứng dụng hỗ trợ học tập theo mô hình Retrieval-Augmented Generation (RAG).
PRN222 chỉ là môn học demo được seed sẵn; hệ thống thực tế hỗ trợ nhiều Subject và không được hard-code
PRN222 làm phạm vi toàn cục.

Ba workflow chính hiện đều đã hoàn thành:

1. Flow 1 - Document Management & Indexing
   - ASP.NET Core MVC Controllers + Views.
   - Quản lý Chapter/Document theo Subject.
   - Upload PDF/DOCX/PPTX.
   - Index nền qua queue/worker.

2. Flow 2 - RAG Question & Answer & Conversation Management
   - ASP.NET Core MVC Chat + Evaluation.
   - Session/history/citation theo Subject và theo user.
   - RAG retrieval bằng pgvector.
   - UI Chat cập nhật tiến trình bằng Server-Sent Events (SSE).

3. Flow 3 - Report & Statistics
   - Razor Pages.
   - Read-only.
   - Truy vấn qua IReportQueryService thay vì PageModel truy cập DbContext trực tiếp.
   - Tất cả document/index/chat metrics đều scope theo Subject.

Conversation History thuộc Flow 2, không phải workflow thứ tư.

4. MULTI-SUBJECT VÀ PHÂN QUYỀN
====================================================================================================

Persisted subject context chính:
- Chapter.SubjectId
- Document.SubjectId
- ChatSession.SubjectId

Vai trò:
- Admin
- SubjectLeader
- Student

Policies:
- ManageUsers     -> Admin
- ManageSubjects  -> Admin
- ManageDocuments -> Admin hoặc SubjectLeader

Flow 1 và Flow 3 ngoài policy còn kiểm tra Subject cụ thể bằng ISubjectAccessService.

Admin:
- quản lý user/role;
- quản lý Subject;
- quản lý bất kỳ Subject nào như operational override.

SubjectLeader:
- chỉ quản lý các Subject được assign.
- assignment lưu bằng ASP.NET Core Identity claim `prn222:managed-subject`.

Student:
- đăng ký public được;
- xem Subject active;
- dùng Chat/Evaluation khi đã authenticate;
- không quản lý academic content.

Flow 2 còn kiểm tra session thuộc đúng authenticated user và Subject request không xung đột với
ChatSession.SubjectId.

====================================================================================================
5. FLOW 1 - DOCUMENT MANAGEMENT & INDEXING
====================================================================================================

Luồng tổng quát:

MVC upload/re-index
  -> persist Document
  -> IDocumentIndexingQueue
  -> InMemoryDocumentIndexingQueue
  -> DocumentIndexingWorker
  -> IDocumentIndexingService
  -> parser tương ứng
  -> TextChunker
  -> ITextEmbeddingService
  -> replace DocumentChunk rows
  -> cập nhật IndexStatus

Parser:
- PDF: PdfPig.
- DOCX/PPTX: DocumentFormat.OpenXml.

Queue hiện là process-local, không phải Redis/RabbitMQ.
Startup recovery re-enqueue các Document còn trạng thái Uploaded/Processing.

Issue #27 đã đóng ở PR #30. Các cải tiến đã merge gồm bounded overlap, Unicode/grapheme safety,
chunking config, PDF two-column ordering và thêm parser regression coverage.

Technical debt còn lại chủ yếu là test/fixture layout phức tạp cho DOCX/PPTX/PDF.

====================================================================================================
6. FLOW 2 - RAG CHAT
====================================================================================================

Luồng backend:

selected Subject
  -> ChatSession.SubjectId
  -> IRagQueryService
  -> ITextEmbeddingService
  -> PgVectorDocumentChunkRetriever
  -> filter Indexed Document theo SubjectId
  -> filter vector_dims phù hợp query embedding
  -> cosine similarity
  -> GroundedPromptBuilder + conversation history
  -> IChatCompletionService
  -> parse citation markers
  -> persist ChatMessages + MessageCitations
  -> trả RagAnswer cho MVC

Các invariant quan trọng:
- session phải thuộc authenticated user;
- Subject request phải nhất quán với persisted session;
- không cố tình fallback sang global corpus trong product path;
- không tạo citation giả khi không có evidence;
- chỉ citation thật sự được reference trong answer mới được persist/render.

PR #35 tăng cường:
- grounded prompt chống hallucination ngoài tài liệu;
- citation marker inline gần factual claim;
- contextual follow-up retrieval khi câu hỏi ngắn tự đứng một mình không tìm được evidence;
- citation excerpt dài hơn cho reader UI.

====================================================================================================
7. SSE TRONG CHAT - KHÔNG PHẢI SIGNALR
====================================================================================================

Endpoint chính:

POST /Chat/AskStream
Response Content-Type: text/event-stream

Browser dùng fetch() và đọc `response.body.getReader()`.

Các event hiện có:
- tool_call
- citations
- delta
- done
- error

Đây là Server-Sent Events (SSE). Project hiện không có SignalR Hub cho Chat.

Một điểm cần mô tả chính xác:
- Controller gọi `IRagQueryService.AskAsync(...)` để lấy kết quả RAG.
- Sau đó controller phát các `delta` theo từ để tạo typewriter experience.
- Vì vậy đây là application-level SSE/typewriter output, không nên gọi là provider-native token streaming.

11. EMBEDDING VECTOR VÀ PR #37
====================================================================================================

Nguyên tắc quan trọng:
- đổi embedding provider/model/dimension => phải re-index toàn corpus;
- đổi chỉ Chat provider/model => không cần re-index.

PR #37 thêm compatibility cho quá trình đổi dimension:
- Gemini batch embeddings gửi outputDimensionality đúng cấu hình;
- pgvector retrieval lọc `vector_dims(Embedding)` bằng dimension của query trước khi cosine distance.

Hệ quả:
- khi migrate dimension, row cũ và row mới khác dimension có thể tạm thời cùng tồn tại;
- row dimension cũ bị loại khỏi retrieval thay vì gây lỗi `different vector dimensions`;
- từng Document trở lại searchable khi re-index xong với cấu hình mới.

Nhưng:
- hai embedding model khác nhau vẫn có thể cùng 1024 dimensions mà vector space không tương thích;
- vector_dims không phát hiện được trường hợp này;
- do đó không được coi same-dimension different-model embeddings là có thể trộn tùy ý.

====================================================================================================
12. ASP.NET CORE DATA PROTECTION - PR #38
====================================================================================================

Trước PR #38, ephemeral web filesystem trên Render có thể làm mất Data Protection key ring khi container
restart/redeploy, dẫn tới cookie/antiforgery token cũ không decrypt được.

Baseline hiện tại:

AddDataProtection()
  -> PersistKeysToDbContext<DataProtectionKeyDbContext>()
  -> SetApplicationName("PRN222-RAG-Assistant")

Key được lưu ở bảng PostgreSQL `DataProtectionKeys`.
CI có kiểm tra bảng này trên PostgreSQL thật.

Vì vậy web container restart bình thường không còn đồng nghĩa với mất key ring nếu database vẫn còn.

14. STORAGE TRÊN RENDER
====================================================================================================

PostgreSQL giữ metadata, chunks, chat, Identity và Data Protection keys.

Source file upload hiện ở:

/app/storage/uploads

Trên Render free web service, local filesystem này là ephemeral. Redeploy/restart có thể làm source file biến mất
mặc dù metadata/chunks trong PostgreSQL còn.

Muốn dùng lâu dài:
- persistent disk trên plan phù hợp; hoặc
- object storage.

Render PostgreSQL free cũng chỉ phù hợp demo/dev, không nên coi là production persistence/SLA.
